# 增强计划任务 / Enhanced Scheduler

AstrBot 的增强型定时主动发言调度器。通过配置多重触发器，实现丰富的自定义未来发言效果。不依赖 AstrBot 原生的"主动能力"。

## 安装与环境

AstrBot `>= 4.27.0`，平台推荐 OneBot v11 即 `aiocqhttp`。cron 触发器依赖 `croniter`。

安装方式任选其一：从插件市场一键安装；在插件页上传 `astrbot_plugin_enhanced_scheduler.zip`；或把插件目录放进 AstrBot 的 `data/plugins/` 后重启、在插件管理页重载。

## 配置入口

WebUI → 插件管理 → 增强计划任务 → Pages 页面。任务的增删改查全部在页面完成。不支持对 bot 发指令管理任务。

插件级配置共四项：

- `poll_interval`，默认 60 秒。兜底轮询间隔，只在任务没有主动触发器、或调度计算失败时生效。正常情况按最近触发点自适应唤醒。
- `log_retention`，默认 100。保留的运行日志条数，最小 10。
- `llm_timeout`，默认 60 秒。单次 AI 生成超时，最小 5。
- `llm_log_retention`，默认 10。LLM 调用记录保留条数，最小 10。

## 一个任务由什么组成

- **触发规则**：一组触发器。
- **任务内容**：执行模式、任务提示文本、时间感知。
- **发送对象**：一个或多个对话 UMO。

### 触发器

触发器分主动、被动两类。主动型负责唤醒触发，被动型负责在触发时检查条件，只在被唤醒时求值。

主动型有两种：

- **周期型 `interval`**：从基准时间出发，每经过 days 加 hours 加 minutes 累加一次。基准时间默认取创建当天的 0 点，可在页面修改。它算的是精确间隔，设 4 小时 21 分，相邻两次就相差 4 小时 21 分，而不是"每 4 小时的 21 分"。
- **cron 型 `cron`**：标准 5 段表达式，依次是分、时、日、月、周，例如 `0 */4 * * *` 表示每 4 小时。

被动型有三种，都是关卡：

- **区间型 `window`**：每天在 start 到 end 之间为真，含端点，也支持 22:00 到次日 06:00 这样的跨天区间。weekdays 为空表示不限定星期几，非空时 0 代表周一、6 代表周日。
- **随机型 `random`**：按概率为真，取随机数小于 threshold 时为真，threshold 为 0 恒假、为 1 恒真。
- **冷却型 `cooldown`**：距本任务上次成功的时间达到冷却时长时为真。冷却计时器按任务独立，不能拿一个任务的冷却去约束另一个任务。

### 组合规则

任一主动型触发，并且所有被动型为真，任务才执行。

因此每个任务至少要有一个主动型触发器，否则永远不会触发，保存时页面会拒绝这种配置。

### 调度行为

调度器并不是轮询式的，保持任务后，插件会算出所有启用任务里最近的那个触发点，等待该时刻醒来进行处理，任务或配置有变化会立刻唤醒重算。

每次醒来，对每个启用的任务依次做四件事：

1. 按各自记录的 `last_fired` 检查主动触发器是否到点触发。
2. 没有主动型到点就跳过；有则实时求值所有被动触发器。
3. 被动全部为真就执行任务；否则只记一条“跳过”日志。
4. 无论被动条件是否满足，到点的主动触发器都会把 `last_fired` 推进到本次触发点，避免同一窗口反复判定。

三条容易踩坑的行为已经处理好：

- 新建与复制任务时，所有触发器的 `last_fired` 都取当前时刻，所以建好之后从未来的第一个点才开始触发；副本默认停用，避免和原任务同时触发。
- 更新任务时按触发器 id 继承原来的 `last_fired`，编辑保存不会重置计时。
- 触发点取距当前最近、且不晚于当前时刻的那一个，宕机期间错过的点只触发一次，不会补发一串历史消息。

## 任务内容

执行模式决定AI行为：

- **固定文本 `fixed`**：直接将特定文本发给目标，不经过 AI。
- **独立 AI `standalone`**：用任务自己的"独立 AI 系统提示"当 system prompt，再使用任务提示词调用 AI。它不注入对话人格，也不广播钩子，与其他插件互不干扰。适用于定时任务与bot人格无关，却又需要AI处理的情况。
- **对话 AI `conversation`**：把包裹后的提示词交给目标会话的 AI，会带上该会话的人格、上下文与记忆等插件注入，但不注入 skills 与 tools。适用于需要以bot自己的人格发言的情况。

AI 返回空内容、超时或报错时，该目标记为失败，不会退化成把原文直接发出去。

`context.llm_generate` 从 AstrBot v4.5.7 起强制要求 `chat_provider_id`，插件从目标 UMO 的会话配置中获取，取不到就直接报失败。

文本留空是一种特殊配置，叫空动作：任务照常执行、照常记日志，但不发消息，并且会推进冷却计时。可以用它观察触发器是否按预期到点。另外，主动到点而被动条件没满足时属于跳过，不算执行，也不推进冷却。

### 提示词包裹与感知开关

两种 AI 模式的提示词都会被统一包裹一层，以便于AI区分聊天上下文和计划任务。

```
<scheduled_task>这是由计划任务自动触发的一次会话，现在时间是 2026年09月21日 星期一 20:34:57，今天是工作日。请根据以下指令进行回复。你的回复将被直接发送给用户。<任务提示词></scheduled_task>
```

上面是时间感知与节假日感知都开启的样子。两个开关互相独立：时间感知默认开启，附加"现在时间是"一段，含年月日、周几与时分秒；节假日感知默认关闭，附加"今天是"一段，需要联网查询。固定文本模式下两个开关都会禁用。

包裹模板内部只用到 `{{time}}`、`{{holiday_clause}}` 和 `{{task_prompt}}` 三个占位符，替换只做一遍，不会二次扫描。

节假日数据取自 timor.tech 的公开接口，按天缓存，同一天只查一次。转成的句子分四种：普通工作日是"今天是工作日"，周末是"今天是周六"，调休上班是"今天是工作日，是国庆节后补班"，放假是"今天是中秋节假期"。查询失败时这条消息不含该句，任务本身照常执行，并且只有查询成功的结果才会被缓存。

## 发送对象

发送对象是 AstrBot 的 UMO 字符串，格式为 `平台:消息类型:标识`，例如 `default:FriendMessage:xxx`。

页面的下拉框会自动列出活跃会话，也可以手动输入。一个任务可以绑多个目标，逐个发送，各自独立记成功与失败。

## 任务 JSON 格式

一条任务就是一个 JSON 对象。页面表单和 JSON 模式编辑的是同一份数据，`upsert_task` 接口收的也是它。

```json
{
  "id": "2d7a1fa4-4dd3-49d5-ad36-e95d764ecdbe",
  "name": "随机问候",
  "enabled": true,
  "triggers": [
    { "id": 1, "type": "interval", "config": { "base_time": "2026-09-21T00:00", "days": 0, "hours": 2, "minutes": 0 } },
    { "id": 2, "type": "window", "config": { "start": "08:00", "end": "20:00", "weekdays": [0, 1, 2, 3, 4] } },
    { "id": 3, "type": "random", "config": { "threshold": 0.5 } },
    { "id": 4, "type": "cooldown", "config": { "hours": 4, "minutes": 0 } }
  ],
  "content": {
    "mode": "conversation",
    "text": "给用户发送一条简短的日常消息。",
    "system_prompt": "",
    "time_aware": true,
    "holiday_aware": false
  },
  "targets": ["default:FriendMessage:xxx"]
}
```

顶层字段：

- `id`：任务标识。不带 `id` 表示新增，带 `id` 表示更新对应任务，新建时插件会自动生成。
- `name`：任务名称，必填。
- `enabled`：是否启用，默认 true。
- `triggers`：触发器数组，至少一个，并且至少要有一个主动型。触发器 id 在任务内唯一。
- `content`：任务内容，见下。
- `targets`：UMO 字符串数组，文本为空时可以为空数组。

`triggers` 每一项由 `id`、`type` 和 `config` 组成，`config` 随类型不同：

- `interval`：`base_time` 是 ISO 格式的基准时间，`days`、`hours`、`minutes` 是周期时长，三者不能同时为 0。
- `cron`：`expr` 是 5 段 cron 表达式。
- `window`：`start` 与 `end` 是 `HH:MM`，`weekdays` 是 0 到 6 的数组，空数组表示不限定。
- `random`：`threshold` 是 0 到 1 之间的概率。
- `cooldown`：`hours` 与 `minutes` 是冷却时长，不能同时为 0。

`content` 字段：

- `mode`：`fixed`、`standalone` 或 `conversation`。
- `text`：任务文本，留空即空动作。
- `system_prompt`：仅独立 AI 模式使用，可为空。
- `time_aware`：时间感知开关，仅两种 AI 模式生效。
- `holiday_aware`：节假日感知开关，仅两种 AI 模式生效。

触发器里的 `last_fired`、任务上的 `created_at`、`updated_at`、`last_success_time` 由插件自己维护，保存时不必提供，写了也会被忽略或按 id 继承。

### 页面里的 JSON 模式

任务编辑弹窗右上角可以切到 JSON 模式，看到的就是上面这份 JSON，也可以直接改。保存走的是与表单完全相同的校验，所以非法配置不会入库。切回表单模式会按 JSON 内容回填，解析失败时只提示错误并留在 JSON 模式。

## 页面用法

任务列表支持编辑、复制、触发一次与删除。触发一次会立刻执行任务内容，忽略触发规则与启用状态，触发期间按钮会进入加载态以防连点。

编辑弹窗分四块：任务名称与启用开关、发送对象、触发器框图、任务内容。

- **触发器框图**：`Start` 扇出到一排并排的主动型节点，汇聚后串行经过被动型节点，最后到 `Target`，直观对应"主动取或、被动取且"。画布可以按住拖动平移，点击节点在下方展开该触发器的配置面板，里面有未来触发时间或上次成功时间，也可以删除；底部按钮用来新建主动型、被动型触发器，并常驻显示下次检查触发时间。
- **运行日志**：每页 20 条，分页浏览。
- **LLM 调用日志**：每页 10 条。进入页面先渲染当页卡片骨架，再串行逐条取正文，取到一条就绪一条；正文要展开卡片时才渲染；图片以徽标展示，点击徽标才真正加载，同一张图片会命中浏览器缓存。

## 典型示例

**喝水提醒**：主动周期型每 4 小时一次，配合被动区间型限定 08:00 到 20:00，内容用固定文本"喝水啦~"，这样只在白天发送。

**随机问候**：主动周期型每 2 小时给一次机会，被动区间型限定白天，被动随机型给 50% 命中率，被动冷却型保证两次至少间隔 4 小时。内容用对话 AI，开启时间感知。

**多个时间源**：主动周期型每 6 小时一次，再加一个主动 cron 型每天 12:00 一次，两者之间是"或"；被动区间型限定 09:00 到 23:00。因为同处一个任务，它们共享同一个冷却计时器，这正是把多个时间源合并进一个任务的意义。

**cron 兼容**：只用一个 cron 型 `30 7 * * *`，内容用固定文本"早安。"。

**空动作**：文本留空，发送对象也可以为空，用来观察触发器是否按预期到点、被动条件是否满足。

## 日志与存储

主动触发器到点时必记一条运行日志，无论被动条件是否满足、是否发送成功。手动触发会额外标注为 manual。日志字段包括时间、任务 id 与名称、各触发器本次真值、被动条件是否全部满足、动作类型、各目标结果与详情。日志存在内存中并持久化到独立的 `run_logs.json`，保留 `log_retention` 条。页面按页向后端拉取，`get_data` 不再携带日志。旧版存在 `tasks.json` 里的日志会在启动时自动迁出。

每次真正调用 AI 还会写一条 LLM 调用记录，成功失败都写，一条记录一个文件，放在 `llm_logs/rec/` 下：

- 首行是元数据，含时间、任务信息、调用来源、模式、目标 UMO、成功与否、耗时、token 用量、正文体积、图片清单与单行预览。日志列表只读这一行，所以翻页很快。
- 次行起是正文，即最终发给模型的完整请求体与 AI 回复，图片位置替换为 `[img:md5.扩展名:体积]` 占位标记。

文件名形如 `20260920-205903.123_随机问候_000042.json`：定宽的毫秒时间前缀让字典序等于时间序，任务名便于辨认，序号防止同一毫秒同名冲突。没有额外的索引文件，最近 N 条直接由文件名排序得到。

base64 图片在写入时被抽离成独立文件，按内容的 md5 命名，放在 `llm_logs/img/` 下。同一张图片在不同记录、不同任务里只存一份，正文里只留占位标记，所以相邻两条内容高度相似的记录不会重复占用磁盘，也不会重复传输。

记录数超过保留条数的两倍时会裁剪最旧的记录，随后扫描剩余记录，回收不再被任何记录引用的图片。如果启动时发现旧版的单文件 `llm_calls.jsonl`，会自动拆分成记录文件并抽离图片，原文件改名保留为 `llm_calls.jsonl.migrated`，可以手动删除。

插件自身结构：

```
astrbot_plugin_enhanced_scheduler/
├── metadata.yaml / _conf_schema.json / requirements.txt
├── scheduler_core.py          # 纯逻辑核心：触发器校验与求值、下次触发计算、合并评估
├── main.py                    # AstrBot 集成：持久化、轮询、执行、LLM 调用、Web API
└── pages/enhanced_scheduler/  # 页面：index.html / index.js / style.css
```

数据写在 `data/plugins/astrbot_plugin_enhanced_scheduler/` 下，升级或重装不会丢：

- `tasks.json`：任务定义
- `run_logs.json`：运行日志
- `llm_logs/rec/`：LLM 调用记录，一条一个文件
- `llm_logs/img/`：记录中的图片，按 md5 命名，跨记录复用
- `llm_calls.jsonl.migrated`：旧版日志备份，仅升级时出现

## Web API

页面通过 `AstrBotPluginPage` bridge 调用这些端点，前缀为 `/astrbot_plugin_enhanced_scheduler`。

任务与配置：

- `GET /get_data`：取全部任务与配置，含预计算的下次触发时间
- `POST /upsert_task`：新增或更新任务
- `POST /delete_task`、`POST /copy_task`：删除、复制，副本默认停用
- `POST /validate`：校验触发器，返回各主动触发器的未来触发点与整体下次检查时间
- `POST /preview_next`：给定触发器返回下次触发时间
- `POST /trigger_now`：立刻手动触发一次
- `GET /get_sessions`：枚举活跃会话 UMO
- `POST /save_config`：保存插件级配置

日志：

- `GET /get_run_logs`：运行日志分页，默认每页 20 条、最新在前
- `GET /get_llm_logs`：轻量元数据分页，默认每页 10 条、最新在前
- `GET /get_llm_log_detail`：按文件名取单条正文，已被裁剪时返回过期错误
- `GET /get_llm_image`：按 md5 加扩展名取图片，返回 data URL
- `POST /clear_llm_logs`：清空记录文件与图片池

## 已知限制

- 组合规则固定为主动取或、被动取且，更复杂的布尔组合请拆成多个任务；每个任务必须至少有一个主动型触发器。
- 被动触发器的下次触发时间无法预测，页面预览只计算主动型。随机型在每次主动到点都会采样一次，采样本身没有副作用，但阈值设得过高会明显降低任务的执行频率。
- 冷却型依赖本任务的上次成功时间。新任务该值为 0，所以首次触发时冷却恒为真；空动作会推进冷却，跳过与发送失败不会。
- 节假日感知依赖第三方接口，查询失败时该条消息不含节假日子句，并且只支持中国的法定节假日与调休。
- 触发时间精度为秒级。跨天区间会被拆成两段，例如 22:00 到 06:00 拆为 22:00 到 23:59 与 00:00 到 06:00。
- 对话 AI 模式下，如果目标会话从未创建过对话，则回退到该 UMO 的默认人格，上下文为空。
